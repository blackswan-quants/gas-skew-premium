# Contributing

**Add only what the current step needs, and be ready to defend every line.**

## Pull requests

- One roadmap step, or part of one. Under ~300 changed lines, not counting `uv.lock`.
- Branch `type/<issue>-<topic>` from `main` (e.g. `feat/12-hh-settlements`), push it to this
  repo and fill in the PR template, with `Closes #<issue>`.
- Merging needs a green CI, a review session and the research lead's approval. PRs are
  squash-merged.
- Add dependencies with `uv add`; each one is justified in the PR.
- Never commit data, `.env` or keys, generated files, or commented-out code.
- Notebooks and PRs show only aggregated results (statistics, figures), never rows of
  vendor data: the data is licensed and this repo is public.

## PR descriptions

Write it yourself (or make it read as if you did), for the reviewer, the way you would
explain the change in person.

- **Title**: what changes, as `type(scope): summary`; it becomes the commit on `main`.
- **What and why**: one to three sentences: the change, then the reason. End with `Closes #12`.
- **How it was checked**: concrete evidence: what you ran or compared, which bug each new
  test catches, numbers before and after. "Tests pass" alone says nothing.
- **Defense**: one short row per added function, test, dependency or config line.
- Say what you are unsure about. Leave out file lists, restated diffs, filler ("this PR
  aims to", "comprehensive", "robust", "seamless") and emoji.
- Most descriptions fit in ten lines plus the Defense table.

## Review session

Before merging, the author walks the lead through every added function, test, dependency
and config line: what it does, why it is needed now, what alternative was considered, and
how it was checked. Anything that can't be justified is removed. You own every line you
submit, whatever tool helped write it.

## Commits

`type(scope): summary`, e.g. `feat(fetch): download TTF option definitions`

- Types: `feat`, `fix`, `refactor`, `test`, `docs`, `build`, `ci`, `chore`.
- Imperative, lower case, at most 72 characters. The body says why.
- One logical change per commit. The PR title uses the same format, because it becomes the
  commit on `main`.
- No "generated by" lines or tool co-author trailers.

## Tests

Only for our own logic, and only if you can name the bug the test catches: maths, parsing,
edge cases, look-ahead. Not for library behaviour, trivial code or real-data numbers (those
belong in notebooks). Synthetic data only, offline and fast.

## Code

- NumPy docstrings on public functions. Comments say why, not what.
- State units: USD/MMBtu for Henry Hub, EUR/MWh for TTF, vol as a decimal, time in years.
- Full type hints. No `print` (use logging). Raise named exceptions, never bare `Exception`.
- Explicit code over abstractions. `assert` financial invariants. Every pricing function
  takes `as_of: date` and never uses later data.
